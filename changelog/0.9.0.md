# 0.9.0 — 2026-10-24

This file accumulates everything landed since 0.7.7. There is no `0.8.0`: that
line was the cross-firmware relocation experiment, and it was dropped on purpose —
moving a calibration between firmware revisions is only safe with a professional
tuner validating the result, and without one the output would be dangerous by
default (the reasoning is in the README roadmap). Three things changed shape:

* **the apply side** — a new engine with an explicit identity policy, built on the
  schema 5.0 recipe specification it reads, exposed as a ladder of four commands
  (`tune-strict` → `tune-shift` → `tune-unique` → `tune-any`) with a matching pair
  of producers (`cook-strict` / `cook-forced`). The engine was verified against the
  flag-driven `tune` byte-for-byte on 47 real pairs **before** that command was
  deleted, which is why the old code is gone rather than deprecated;
* **the TUI** — the 2 625-line single module was retired and rebuilt screen by
  screen on top of the API gate: BOOT, HOME, IDENTIFY, INSPECT, MAPS, COOK, DIFF,
  APPLY, BATCH, CONTRIBUTE and HELP;
* **the contribution wizard** — a screen, a wider dump intake, and a generated
  extractor that now measures the identity instead of leaving four `TODO`s.

### Added

- **The DIFF screen — what changed between two dumps, table by table.** COOK
  answers "make this pair portable"; DIFF answers the question that comes first,
  and it is now a screen of its own (HOME card 3) with the pair shared in both
  directions: `[D]` in COOK hands the two files over, `[C]` in DIFF hands them
  back. The summary never lets the explained part stand in for the whole — the
  reference pair has 34 changed tables and **69 changed regions no table accounts
  for**, and both are shown, with `[U]` listing the second and `[⏎]` rendering
  both sides of a region byte by byte. `[D]` opens the selected table as
  stock / tuned / **Δ** per cell against its measured breakpoints (a view the CLI
  cannot give at all); `[P]` writes both sides as SVG using those same
  breakpoints; `[X]` writes the delta as long-form CSV with breakpoints. Filters
  (`changed` / `realigned` / `no axis` / `all`) keep exactly what their labels
  say, and axis-backed tables rank above inferred ones — a `no axis` table's
  `-100%` is computed against row shapes the scanner guessed and must not lead.
  A region's size is printed as "largest N B", never as a changed-byte total: a
  region is an extent, and a number that cannot be reconciled is worse than two
  honest ones. Nothing is named anywhere on the screen.
- **The product is now tested off Linux.** Wheels were built for macOS and
  Windows, but the suite had only ever *run* on Ubuntu — so "the TUI works on
  Windows" was an assumption. A `portability` job now runs the TUI and console
  tests on `windows-latest` and `macos-latest`. It is advisory (`continue-on-error`)
  until it has been green twice, because the suite was written on Linux and the
  first run is worth reading rather than obeying.
- **Console output is UTF-8 by default.** On Windows a redirected stream uses the
  ANSI code page, so `openremap identify x.bin > out.txt` raised
  `UnicodeEncodeError` on the first em dash — and the copy is full of `→`, `✓`,
  `⚠`, `Δ` on purpose. `openremap.console.force_utf8()` reconfigures `stdout`/
  `stderr` (with `errors="replace"`, so a glyph a terminal cannot draw becomes
  `?` instead of killing the command) and is a no-op on a UTF-8 stream. Wired into
  the CLI entry point and the JSON-RPC transport; the TUI's own terminal handling
  is left alone.
- **The picker lists the drives on Windows.** A tree rooted at `C:\Users\…`
  can only climb as far as `C:\` — no arrow key leaves a drive — so the drives are
  named in the header and typed into the path field (`D:`, normalised to `D:\`).
  No jump key is invented: in this screen a printable key belongs to the path
  field. The row is hidden off Windows, where drive letters are not a concept.
- **CI runs the TUI off Linux — and that is how these were found.** The new
  `portability` job (windows-latest + macos-latest) caught two real defects in the
  picker on its first run, plus one test that only worked because the corpus was
  present locally. `D:` is rewritten to `D:\\` only when it is a *bare* drive spec;
  the first version also rewrote UNC paths (`\\\\server\\share` came back with a
  separator nobody typed). The drive row's test asserted "hidden" — true on POSIX,
  false on Windows — and now forces both directions. And `TestClearing` in
  `test_recent.py` used the corpus without the guard its siblings had, so it failed
  on every platform where `tests/data/` is absent, which is all of CI.
- **The file picker's path field stopped failing silently.** Typing a folder that
  does not exist left the tree exactly where it was, with no message at all —
  against the picker's own stated rule that a rejected file is always named. It
  now says `no such folder: …` and stays open. The same path also stops mangling
  the Windows idiom for changing drives: `D:` is *drive-relative* there (meaning
  "the current directory on D:", often not a directory at all), so it is read as
  `D:\` — while on Linux and macOS the identical text is a filename and is left
  alone.
- **`hex_region`** — a byte range of a binary as hex, so the TUI never opens a
  file itself. **`map_image` accepts the caller's breakpoints** (`x_axis` /
  `y_axis`) instead of re-deriving them from a descriptor that may not carry the
  offsets: the DIFF screen already measured them, and the picture must not fall
  back to cell indices while the grid next to it shows real breakpoints.

- **The apply side says out loud that it does not correct checksums.** Every
  apply command printed `APPLIED`, a sha256 and the bytes written — all true, and
  all about the *recipe*. Nothing in this engine rewrites a stored checksum, so
  the written file is expected to be stale wherever the family carries one, and
  the operator learned that from the ECU instead of from us. The report now
  carries a measured verdict on the bytes it produced
  (`report.result.checksums`: `ok` / `fail` / `skip`), shown by the CLI and by the
  TUI's `CHECKSUMS` row, together with the command that re-checks the written
  file. It is a disclaimer, never a refusal: a stale checksum does not make the
  recipe wrong, it makes the file unflashable. `skip` is the honest answer for a
  family whose checksum we have never cracked (Bosch EDC17 among them) and is
  never presented as a pass. Cost: one detector pass, 22–62 ms on a 4 MB dump.
  Every successful apply also prints a standing disclaimer, set apart from the
  check rows: **OpenRemap does not correct checksums automatically**, a tune that
  will run in a real vehicle must be reviewed by a dedicated tuner shop, and the
  supported use is right to repair and track racing — not modifying an everyday
  car. It is a constant in the report (`result.disclaimer`), so the CLI and the
  TUI cannot drift apart on it.

- **The wizard now says what your dumps can prove.** A marker is "stable across
  your dumps", and that is evidence of a family signature **only if the dumps are
  different calibrations** — two dumps of one calibration cannot, with any
  algorithm, tell a family token from that calibration's version string. Measured
  on two real families: Bosch EDC17 with two dumps of one calibration produced an
  extractor covering **0 of 17** known dumps; two dumps of different calibrations
  produced one covering **14 of 17**, exactly the set the hand-written marker
  covers. Denso SH7058: **22/35** from one model year with a marker made of
  repeated data, **35/35** from two dumps six years apart using the ECU's own OS
  banner. So `analyze` now reports `calibration_diversity`
  (`same-calibration` / `different-calibrations` / `near-identical` /
  `distinct-builds`, by identity when the family is known and by shared bytes when
  it is not), the CLI and the CONTRIBUTE screen print it *before* the candidates,
  and the PR description gains a **What your dumps can prove** section. The intake
  copy changed with it: the advice was "two or more dumps", which counts dumps
  when what matters is that they are different calibrations.
- **A repeated data pattern can no longer lead the candidate ranking.**
  `signatures.repeated_motif()` flags a run built from one short motif (≥6
  repetitions over ≥60% of its length, any alignment): the measured
  `'gCaCA$3:f3F$&j4j3j#WD$3TD$3TD…'` — 152 printable bytes, 120 of them `$3TD` —
  ranked first and was recommended. It stays in the list with its reason, like
  every other generic run, but it can no longer be the recommendation.

- **The contribution wizard measures the identity, not just the marker.** The
  generated skeleton used to ship with every `extract()` field as `None` and a
  `TODO` — a shape, not a contribution — while the wizard had already measured the
  very fields it left blank. It now fills software version, hardware number,
  variant and calibration version from the *pattern* that found them in the
  contributor's dumps, so the skeleton's `match_key` agrees with the engine's from
  the first run. The pattern is what travels, never the measured value: a value
  copied in as a literal would match exactly one calibration, which is the same
  mistake the wizard exists to prevent in `can_handle()`. Whatever the dumps could
  not decide stays a `TODO`, and the report lists which. The PR description gains
  a **Fields measured** section, because the measurement a reviewer most needs
  (the ident descriptor carrying variant and calibration version) used to reach
  nobody: it was in the JSON and in none of the files handed over.
- **`contribute extractor` takes as many dumps as you have.** The positional
  argument is variadic (`a.bin b.bin c.bin`), mixing freely with the repeatable
  `--also`. Two dumps are the minimum that can show a marker is stable; there was
  never a reason for the command to cap the evidence at two.

- **`openremap tune-strict` — apply only when every check passes.** A new
  command with **no safety flags at all**: no `--force`, no `--skip-validation`.
  The command *is* the policy. It runs, in order: recipe validity (type, schema,
  known sections/fields, and a contract that agrees with its own payload), the
  recipe's identity floor, declared size, **same firmware** (`match_key`, with a
  single identification reused for the whole report), every original byte at its
  recorded offset — with a dedicated "already patched" message instead of a bare
  mismatch — the anchored search, **`shift == 0`**, post-verification, and a byte
  accounting pass that refuses if anything changed outside the declared ranges.
  Reports but never blocks: anchor look-alike count and the flash-region split. Exit 0 applied / 1 refused / 2 bad
  input.
- **`openremap tune-shift` — one rung looser, one thing tighter.** Applies a
  recipe when the target is the **same firmware** but the change is found at a
  displaced offset (±2048 bytes instead of the recorded one); the shift is
  reported per instruction. In exchange, an anchor with more than one copy in
  the search window becomes a **refusal**: once a shift is allowed the engine
  really chooses between candidates, so "closest match" is no longer safe. This
  is strictly safer than the removed `tune`, which allowed shifting *and* let
  ambiguity pass with a warning. Both commands share one pipeline; only the rule
  set differs.
- **The full apply ladder — `tune-unique` and `tune-any`.** Four commands, one
  pipeline, each dropping exactly one rail in a fixed order: the firmware label
  first, then positional strictness, then anchor uniqueness.
  `tune-unique` applies to a target that **cannot be identified at all** — the
  common case for obscure or modified dumps, which the identity-gated commands
  must refuse — on two independent proofs of position: every original byte at
  its recorded offset *and* every anchor unique in the search window.
  `tune-any` is the loosest: no identity, a displaced anchor accepted, an
  ambiguous anchor reported instead of refused. Both still enforce a valid 5.0
  recipe, the declared size, verification and byte accounting, and both still
  honour the recipe's `identity_floor` — a recipe that declares it needs
  firmware identity cannot be applied by an identity-free command.
- **`openremap cook-strict` / `cook-forced` — the schema-5.0 producer.** Two
  commands, one pipeline, mirroring the apply ladder. `cook-strict` requires
  every anchor to be unique and declares `identity_floor: any` — a
  self-verifying recipe that **every** apply command accepts, including the
  identity-free ones. `cook-forced` accepts non-unique anchors (a change inside
  blank flash or padding) and declares `identity_floor: firmware`, so only the
  `match_key`-verifying commands will use it. Both refuse a pair of two
  different firmwares, both verify their output against the apply-side reader
  before writing it, and **neither excludes anything**: no VIN, no checksum, no
  "volatile" bytes — anything suspicious becomes an instruction flag.
- **Schema 5.0 recipe specification** (the contract `cook-strict` /
  `cook-forced` write and the apply engine reads). 5.0 replaces the overloaded
  `metadata.portability` stamp with an explicit `contract` block —
  `identity_floor`, `anchors_unique`, and two tri-state flags (`true`/`false`/
  `null` for "unknown"). Four of the five fields are **re-derivable from the
  payload**, so a consumer detects a doctored or stale contract instead of
  trusting it. Also new: full `source.identity`, `tune.sha256`, and a stored
  `regions` summary (the old cook computed it and threw it away).
- **New apply engine** in openremap/core/services/recipes/apply/ (contract
  reader, identity policies, pipeline, report). It **composes** the existing
  primitives (`ECUStrictValidator`, `ECUPatcher`, `ECUPatchedValidator`) rather
  than reimplementing them, so the codebase keeps exactly one safety core.
- **Four apply composites** in the API registry (`apply_strict`, `apply_shift`,
  `apply_unique`, `apply_any`) — path I/O plus `GuardError` translation and
  nothing else — and their four CLI commands, one per rung of the ladder.
- **Internal specs**: schema 5.0, the tune-strict rule set, and a neutral
  catalogue of every check the apply side can perform (what each one reads,
  what it can conclude, and the six things it cannot know without the stock
  binary).
- **The CONTRIBUTE screen (TUI) — add a family from the inside.** The wizard that
  measures your own dumps for a family the engine does not recognise now has a
  screen: add one or more dumps, measure (local only — who claims them, which
  byte runs are stable, the candidate signatures), name the brand and family,
  then render the contribution and write its four artifacts (extractor, test,
  report, fixture) into the workspace. The promise is on screen: **your dumps
  never leave the machine**, and what gets committed is a synthetic fixture
  carrying only the marker. While the collision check has not run, the screen
  says so instead of implying the marker is safe.
- **The TUI remembers what you used.** Every screen that actually works on a
  file records it (`dump`, `recipe`, `patched`, `folder`) into the workspace
  `.state.json`, and HOME lists the last five as something you can open: `R`
  focuses the list, `↑↓` chooses, `Enter` opens the screen that fits —
  IDENTIFY for a dump, APPLY with that recipe loaded, BATCH on that folder. It
  survives a restart (written immediately, pruned of files that vanished), keeps
  one row per file however many screens touched it, and `D` (or `Delete`) clears it
  without touching a single file. Before this the list was decorative: one call
  site recorded anything at all, and nothing could be opened from it.
- **Four gaps closed in the TUI.** `[V]` in COOK audits the triplet (stock +
  tuned + recipe) and says whether applying the recipe reproduces the tuned file
  byte-for-byte; `H` (or `?`) on HOME opens a HELP screen whose capability list is read
  from the engine's own registry (so it cannot go stale) with the family
  reference one key away; `[D]` in APPLY opens the recipe's instruction list
  (offset, bytes, region, anchor, flags); and BATCH gained a `vin` column that is
  opt-in — `scan_vins` reports 17-character *candidates* at ~0.45 confidence and
  only shows a VIN string when the check digit actually decodes, so a candidate
  reads `~0.45` and never masquerades as a registration.
- **The family reference moved out of the CLI.** `cli/commands/families.py` held
  a 350-line table of eras, vehicles and identifiers — domain data, in a
  presentation module, unreachable by any other consumer. It is now
  `core/manufacturers/families.py`, read by the CLI and the TUI through a new
  `families` API method.
- **The BATCH screen (TUI) — what is in this folder.** Classifies every dump in
  a folder with every extractor (`scanned` / `sw_missing` / `contested` /
  `unknown` / unreadable) and shows which is which, with a live count, the
  measured pace and `≈` time remaining, `Esc` to stop and keep what is done, and
  duplicates counted by md5 (the reason to batch a folder at all: 19 of 205 in
  the EDC16 fixture). Organising is a **second step**: `O` shows where each file
  would go without touching anything, then `C` copies or `M` moves — copying is
  the default, because a copy cannot lose a dump.
- **The scan's file rules moved into the service layer.** Which files a scan
  covers, which folders it must not re-scan, where a classified file would be
  filed, and the copy/move itself lived in `cli/commands/scan.py` — file I/O and
  policy inside a presentation module, with a second consumer (the TUI) about to
  copy them. They are now `core/services/scan_organize.py`, used by both, with
  two new API methods so a UI can classify **one file at a time** and show real
  progress instead of waiting for one long call.
- **`openremap recipe-info` — read a recipe without applying it.** Schema,
  instruction count, `identity_floor`, the two files it was cooked from (with
  their sha256), the producer, and the change statistics. It runs the *apply
  engine's own 5.0 reader*, so a recipe that fails here would be refused there
  with the same rule id (A1–A5, A12). A recipe was previously only readable by
  running it against a target.
- **The APPLY screen (TUI) — recipe + target in, a patched copy out.** Runs
  `tune-strict` first; when it refuses, the refusal's own rule decides what may
  be offered next, and the offer is printed with what it costs
  (Γ2 → `[U] tune-unique`, Γ7 → `[S] tune-shift`, Γ4/Γ7/Γ8 → `[A] tune-any`).
  Any other refusal says plainly that no looser rung helps. The result shows all
  fourteen checks with their rule ids and measured details, and the one claim
  worth making loudly: the patched bytes are **byte-identical to the file the
  recipe was cooked from** (its `tune.sha256`). Nothing is written over the
  input; `[W]` writes into the workspace `tunes/`, with the path shown first.
- **The COOK screen (TUI) — two files in, one recipe out.** Picks the stock and
  tuned files and identifies both in the background, so the fact cook itself
  checks (same firmware) is on screen *before* the run; the cheap facts (same
  size, same path) are read with `os.stat` and shown at once. The next action is
  a line of its own (`→ press [Enter] to cook this pair`), not a hope that the
  key bar is noticed. The mode is treated as a property of the pair, not a
  preference: the looser rung (`cook-forced`, `identity_floor: firmware`) is
  offered only when the engine refuses *because* anchors repeat, with the cost on
  the key itself. The report shows the engine's own numbers (instructions, bytes,
  maps, regions, flags, contract, fingerprint), and saving writes into the
  workspace `recipes/` at a path printed *before* the key is pressed — a second
  press overwrites. Until it is written, a warning row above the keys says
  `⚠ NOT SAVED` with the full target path — a recipe in memory is a recipe that
  a stray `q` deletes.
- **`openremap map-image` — a table drawn properly, as a file.** Picks a table
  from a scan (`--list` shows them, `--offset`/`--top` choose one) and writes an
  SVG with every cell's value, coloured by value, the **breakpoints stored in
  the binary** on both axes, a colour scale, and a footer stating what the
  picture does not claim. SVG because a terminal has no pixels: character cells,
  fonts, colour depth and aspect ratio are outside our control, so a map painted
  in characters can look wrong while claiming to be data. Scales to any size,
  prints, opens in a browser, needs no image library.
- **The TUI lists tables instead of painting them.** The MAPS screen is a
  full-width list (offset, shape, cell, score, heuristic label) with one line of
  measured facts and one line of shape for the selection (a sparkline of row
  means); `P` writes the SVG next to the dump. An earlier draft painted a heat
  map, iso-contours and a rotatable 3D surface in the terminal — it was removed
  on purpose: it cost three view modes and six keybindings to show something
  that depends on the terminal and cannot be trusted as data. The interactive
  2D/3D view belongs to the GUI, where there is a GPU.

### Changed

- **`health.check_checksums` is public now** (was `_check_checksums`). It is the
  right primitive for "does anything we know how to verify still verify?" — a
  detector pass, not the brute-force sweep — and the apply side asks it about the
  file it just wrote.

- **A field that is constant in your dumps is no longer advertised as a
  signature.** The wizard's own advice — "constant — usable in `can_handle()` or
  a fixed field" — is how a marker made of one calibration's version string gets
  generated: two dumps of the same calibration cannot distinguish a family token
  from that calibration's version string. The label now says what the evidence
  supports (a fixed field, not proven as a signature), and 80-column line
  wrapping no longer breaks it mid-word.

- **The low-entropy flag no longer fires on a verified-unique anchor.** A unique
  anchor was expanded (up to 512 bytes) until it occurred exactly once, so it is
  proof of position — flagging it produced two lines of noise per change, with
  40 of 41 cases already covered by the `CODE_AREA` region tag. The scanner now
  flags only anchors whose uniqueness is *not* verified (`WEAK_ANCHOR`), and the
  contributor guide states the bar: a flag must point at something the reader can
  act on.
- **No checksum data in the recipe, at all.** `checksum_regions`, the
  `checksums_touched` tri-state and any "excluded checksum bytes" notion were
  removed from schema 5.0 before a line of the new cook was written. Rationale,
  in one sentence: a tuner recomputes checksums after flashing anyway, so
  writing a donor's checksum bytes is harmless — while a *wrong* stored
  checksum region would silently drop real tune bytes, and that failure is
  invisible and unrecoverable. Checksum knowledge stays a live capability over
  a binary (`openremap checksum`), never data carried from a dump.

- **The CLI package moved back to the top level: `openremap/cli/`** (was
  `openremap/core/cli/` since 0.7.3). The CLI is a *consumer* — it sits beside
  `openremap/api/`, not inside the engine. `core/` now holds only the engine
  (services, arch, manufacturers). Imports, packaging entry points
  (`openremap = openremap.cli.main:main`), tests and docs were updated in one
  sweep.
- **The 2 625-line single-module TUI was retired and deleted.** A from-scratch
  rebuild replaced it screen by screen, and once every screen existed the old
  copy was removed rather than archived: a second implementation nobody runs is
  the thing that gets edited by mistake. `openremap-tui` **stays** — it now points at
  `openremap.tui.main:run`, which launches the new app — and bare `openremap`
  prints the command surface instead of launching nothing.

- **Checksum knowledge is tri-state and informational.** `false` now requires
  *positive coverage* (a profile that enumerates every checksum block); anything
  else is `null` = unknown, and the report says so. Measured on the real
  EDC17C66 pair: **zero** schemes verify across the whole sweep space and no
  family detector recognises the file — for that dump the honest answer is
  "unknown", not "fine".

### Fixed

- **The Bosch software-version pattern truncated the real thing.**
  `1037\d{6,10}` read `1037541778126241V0` as `10375417781262` — a version no
  binary carries, so a `match_key` built from it could never match. The pattern
  now keeps the revision suffix, exactly as the shipped extractors do.
- **An ident descriptor past the header window was reported as absent.** The
  family-name suggestion scan stopped at `0x20000`, but a 4 MB Bosch dump keeps its
  authoritative descriptor at `0x40E14`, so the wizard said "no descriptor" for a
  dump that has one. It scans the file now, bounded by an early exit rather than by
  a window.
- **`--measure-only` inside a clone claimed the clone was missing.** The reason the
  collision check was skipped is the flag, not the machine; the message inferred it
  from `collisions_checked`, which is `False` in both cases.
- **A generated extractor could crash on its own fixture.** Keys set only inside
  `if match:` were absent when the fixture carries the marker and nothing else, and
  the verification pass runs `extract()` on exactly that fixture.

- **Three screens were hiding their key bar.** `height: 1` plus a top border
  leaves zero rows for text: the bindings existed, the widgets existed,
  `.render()` returned the right string, and the bar was invisible on MAPS,
  INSPECT and COOK. The bars have a content row now, and a test measures the
  *content box* of every screen's bar instead of trusting the renderable.
- **Cooking a file against itself is a refusal, not a crash.** Two identical
  files diff to nothing; the producer built an empty recipe and its own
  verification then failed with
  `RuntimeError: cook produced a recipe the apply engine refuses (A12)`. The
  easiest mistake a user can make now reads as a rule: `empty` — "the two files
  have no differences".
- **The apply engine speaks English too.** Every check name, refusal message and
  next-step line in `apply/` was Greek, and both the CLI and the TUI print them
  verbatim — a check table full of "ταυτότητα firmware" in an English product.
  Translated (~155 lines); the rule ids (`A1`, `Γ2`, `Δ4`) stay as they are,
  because they are the vocabulary of the rule documents. Two refusals also
  stopped pointing at the deleted `openremap tune` command.
- **Cook messages are in English.** The producer's refusal messages, notes and
  mode summaries were Greek, and every consumer (CLI, TUI) prints them verbatim.
  Translated and pinned by a test; the apply side is still pending and goes with
  its own screen.
- **The native engine no longer freezes the process while it works.** Every
  heavy Rust function held the interpreter lock for its whole run, so a 4 MB
  scan (≈7 s) or analysis (≈21 s) blocked *everything else* in the process —
  other threads, event loops, any host UI. Each one is now a thin shim that
  releases the GIL around its `*_inner` body (`py.detach`): the same work takes
  the same time, but the caller stays alive. A 4 MB scan now holds the main
  thread for **46 ms** instead of **6.4 s**. Guarded by
  `tests/api/test_gil_release.py`.
- **`tune-unique` no longer refuses an ambiguous anchor.** With the bytes pinned
  at their recorded offset and `shift == 0`, the patcher's "closest match" is the
  expected offset by construction — the number of look-alike patterns elsewhere
  in the ±2 KB window cannot change where the write lands. It is now reported,
  exactly as `tune-strict` does with the same positional guarantee. The rule the
  ladder follows: *ambiguity is decisive only where a shift is allowed*, because
  that is the only place a choice actually happens.
- Applying a recipe that was already applied now says so instead of reporting a
  generic original-bytes mismatch.

### Removed

- **The flag-driven apply engine and its commands are gone**: `openremap tune`,
  the atomic `patch` method, and the services behind them
  (`recipes/tune.py`, `recipes/patch.py`). Their behaviour lives on in the four
  policy commands, and the parity record for 47 real stock/tuned pairs is pinned
  in `tests/tuning/parity_goldens.json` — the tests no longer need the old code
  to prove nothing shifted.
- **The 4.x producers are gone**: `openremap cook`, `openremap cook-volatile`,
  the `cook` / `cook_volatile` methods, and `recipes/cook.py` +
  `recipes/cook_volatile.py`. `cook-strict` / `cook-forced` replace them, and the
  volatile classifier itself stays only because `audit` still reads legacy 4.5
  documents.
- **`merge` and `audit` now read recipe provenance through
  `recipes/recipe_facts.py`** (source-first, 4.x `ecu` fallback), and a merged
  recipe is written as schema 5.0 with a contract verified against the apply-side
  reader.

### Deprecated

- **Schema 4.x recipe documents.** The commands that wrote them are gone, and the
  apply engine refuses one with rule `A2` and a pointer to `cook-strict` /
  `cook-forced`. `audit` and `merge` still *read* 4.x (that is what keeps old
  provenance legible), so the format is retired for application, not erased.
