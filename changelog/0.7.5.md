# 0.7.5 — 2026-08-30

This release rounds out OpenRemap's CPU coverage and adds a new way to read
code. A new `routine` command turns any routine into readable pseudo-code
without needing Ghidra, and the decoder now understands many more ECU
families — including the 8051- and MCS-96-based ones, which had no decoder
at all until now. We also audited every family's CPU so it's clear what's
covered and what still needs work. On the security side, the Rust↔Python
bridge (PyO3) was upgraded to close two vulnerability advisories.

### Added

- **`routine` command** — `openremap routine <bin> <offset>` prints the
  instructions around an offset as one readable line each. The decoder is
  picked automatically from the ECU family (`--arch` overrides it), and
  covers C166, TriCore, SuperH, x86, M680X, 68K and PowerPC (8051 and
  MCS-96 have xref decoders but no routine renderer yet).
- **8051 decoder** — the Rust backend now disassembles 8051 (MCS-51) code,
  covering families like M1.8, M2.x, MP9, M4.x, Mono, SIMOS and Simtec56.
  Every opcode length is pinned against an independent reference (the
  `sizes_match_at51_oracle` cargo test, all 256 opcodes), and instruction
  boundaries matched the at51 oracle 100% on the measured corpus subset
  (M2.9, MP9, M4.3, Simtec56, SIMOS — 312,202 boundaries).
- **MCS-96 decoder** — the same for the 8096 family, serving EDC1 and EDC3.
- **M680X / 68K / PowerPC** — these CPUs are now wired into the decoder
  table, reference extraction and the pseudo-code renderer: M1.x, M3.x,
  MP3.x/MP7.2 and LH-Jetronic (M680X); M1.5.5/M1.55 and IAW 4LV (68K);
  MJD 6JF (PowerPC).
- **Arch census** — an audit (`scripts/census_arch.py`) of which CPU each
  corpus family actually uses, with a triage of what's already covered and
  what needs a new decoder.

### Changed

- The CPU table gained `M5`/`ME1.5.5` (C166) and `MED17` (TriCore), and was
  corrected after the audit: EDC16 + MED9 are TriCore, Simtec56 + M4.x are
  8051, and the previously-unmapped 8051/MCS-96 families now use their new
  Rust decoders.
- CPU auto-detection now tries capstone first (TriCore → SuperH) and C166
  last.

### Fixed

- `c166_disasm` register decoding — a value that was printed as `R244` now
  correctly prints as `R4` (it's a register only in one specific case,
  otherwise a special-function register).
- CPU auto-detection no longer mislabels unknown families as C166.
- The `commands` cheat-sheet is no longer a hand-maintained list that
  drifted — it's generated from the CLI itself, so it always includes every
  command (including `analyze`, `convert` and `routine`).
- Three extractor docstrings corrected: M2.x, MP9 and M4.x are 8051, not
  68xxx.

### Security

- **PyO3 0.25.1 → 0.29.2**, closing two advisories in the Rust↔Python
  bridge:
  - [RUSTSEC-2026-0176](https://rustsec.org/advisories/RUSTSEC-2026-0176) —
    out-of-bounds read in the `PyList`/`PyTuple` iterator methods
    `nth`/`nth_back`.
  - [RUSTSEC-2026-0177](https://rustsec.org/advisories/RUSTSEC-2026-0177) —
    missing `Sync` bound on `PyCFunction::new_closure`.
  Neither was reachable from OpenRemap's own code (the extension uses PyO3
  only to register functions taking plain bytes/integers), but the
  vulnerable code was compiled in, so the upgrade removes it outright.
  Thanks to **@begininvoke** for reporting the first advisory — see
  [issue #1](https://github.com/v-arapidis/openremap-core/issues/1).
