# 0.7.6 — 2026-09-06

This release turns two previously-unidentified lines into full identities and
fixes VAG part-number detection: a new ME7.9.x Bosch extractor, a new Siemens
GS20 (BMW AGS) extractor, and a shared, false-positive-proof VAG part-number
scanner for the EDC15/EDC16/EDC17/EDC3.x extractors. All changes were
validated against the full corpus before and after, with zero regressions.

### Added

- **ME7.9.x (ME7.9.10) extractor** — new Bosch family covering the
  Fiat/Alfa/Lancia 1.4 T-Jet and PSA variants (2006+). These 832KB dumps
  were previously unidentified: their ident block at 0x10000 uses the
  `ZZ<<` dialect, which the classic ME7 extractor's `ZZ<digit>` guard
  deliberately skips. The new extractor keys on that dialect plus the
  `ME7910`/`ME7.9` family markers in the calibration area, and extracts the
  10-digit SW number, the `0261…`/`0261S…` HW number and the match key
  (`ME7.9.10::<sw>`). Registered right after the ME7 extractor — the
  corpus-wide claims sweep shows it claims only the two dumps that were
  previously unclaimed (no detection reordering anywhere else).
- **Siemens GS20 extractor** — new family covering the 4 previously
  unidentified 64 KB dumps (`tests/data/ECUs/Siemens/GS20/GS20_90C0_64KB*`).
  Oracle ground truth (ms4x wiki + a community BMW flash-tool corpus): GS20
  is a Siemens BMW automatic-gearbox controller (AGS), HWNR `7544721`.
  Detection is a 64 KB
  size gate + the header code `GADC9010` + the footer project string
  `G2210_0090C0AD10` (both corpus-unique; `G2210_` is the oracle's GS20
  ident key). Extracts `software_version` (7-digit `7557997`) and
  `calibration_id` (`GADC9010`) with match key `GS20::<sw>`; `hardware_number`
  stays `None` because the oracle HWNR `7544721` is not stored as ASCII in the
  dumps. Field mapping is heuristic — the oracle's GS20 ident numbers are all
  7-digit (HW/ZB/SW), so `7557997` is kept as the version identifier for a
  stable match key (documented in the extractor). A before/after corpus scan
  (1,685 files) shows exactly those 4 files flip from unidentified → GS20 and
  nothing else changes.
- **`analyze --xref-mode v2`** — opt-in code-reference mode whose confirmation
  bonus is score-gated: a table earns the +0.06 only when it is already
  high-confidence (structural `score >= 0.85`, the corpus-validated
  "calibration, never code" floor) AND referenced by code anywhere in its data
  block. Decoder calibration (load-base detection + arch cascade) stays
  byte-identical to the default `v1`. Measured on 19 real corpus bins:
  base/arch unchanged (19/19), bonus tightened 396 → 40 with all 40 high-score
  referenced maps kept (median boosted score 0.767 → 0.882). The design
  evolution (v2.0 span-gating → v2.1 first-cell → v2.2 score-gated) is
  documented in `core/services/maps/xrefs_v2.py`.
- **Declarative workflow engine** — a small engine (`openremap/api/workflows/`)
  turns `.toml` step lists into registered methods with `kind="workflow"`. A
  workflow is a linear, unconditional pipeline: each step is a `call` to a
  registered method with `$input.*` / `$prev.*` / `$<as>.*` data plumbing, and
  the last step (or an explicit `output`) is the result. Built-in workflows
  auto-load on import; extra dirs load via `load_workflows()` or
  `OPENREMAP_WORKFLOW_DIRS`. Ships `identify_cook` (identify both binaries →
  cook) as the reference workflow. No code execution — dropping a `.toml` is
  the third-party extension surface. Malformed or invalid `.toml` files in
  user-supplied dirs are skipped with a warning (the built-in workflows fail
  fast), so one bad extension file cannot break `import openremap.api`.

### Changed

- **diff-maps cell machinery moved to Rust** — `_read_cells` (strided path),
  `_best_alignment`, and `_diff_cells` in `cli/commands/diff_maps.py` are now
  thin wrappers over a new `_rs/src/maps/diff_cells.rs` module
  (`read_cells` / `best_alignment` / `diff_cells`). The new Rust `read_cells`
  is a shared primitive that also replaces the duplicated `_read_cells` copies
  in `map_classifier.py` and `map_exporter.py`. The per-cell Python loops are
  gone (~1.2 s of the ~5.9 s `diff-maps` CLI on the 4 MB pair, est. ~50–100×);
  parity is byte-exact — verified 1:1 against the original pure-Python
  implementations on the real 4 MB tune pair (5,257 `read_cells` tables incl.
  398 strided, 2,432 `best_alignment` pairs, 2,432 `diff_cells` pairs, the
  latter bit-exact including the raw unrounded floats) plus ME7.1.1 and MS43.
- **Shared VAG part-number scanner** (`manufacturers/bosch/_vag.py`) — a
  letter-guarded regex used by the EDC15/EDC16/EDC17/EDC3.x extractors'
  OEM part-number resolution. It fixes two real gaps:
  - part numbers with a **digit** at position 3 (`038906016L`,
    `045906019BQ`, `022906032CS`) were missed by the old
    `0[2-9][A-Z]…` pattern;
  - platform-code prefixes (`4B0906018DF`, `3B0907401`) were missed
    entirely.
  The letter-content guard keeps all-digit runs (Bosch HW `0261…`/`0281…`,
  SW `1037…`, 9-digit calibration codes) out — a 654-file sweep across
  non-VAG families shows zero false positives, down from the naive
  broadening's 3.
- EDC15 non-Format-D dumps (ALH/AGR etc.) and EDC3.x dumps whose ident
  parsers produced no OEM number now fall back to the shared scanner.
- **Denso Subaru family relabel** — the petrol `ecu_family` labels were one
  CPU generation off (confirmed by two independent oracles). Detection is
  unchanged (each size bucket still maps to one clean CPU); only the names
  shifted: `SH7055` (160/192 KB) → `68HC16Y5` (Motorola HC16), `SH7058`
  (512 KB) → `SH7055` (SuperH), `SH72531` (1 MB) → `SH7058` (SuperH). The
  arch table no longer disassembles the 16-bit units as SuperH (capstone has
  no HC16 support), and the health map-count envelopes were re-keyed to the
  new names. Verified on the full corpus before/after — zero claim changes.
- **API thin-gate refactor** (internal, no output change) — every
  `*_binary` / `*_recipe` / `*_one` / `*_image` core function moved out of
  `openremap/api/commands/` + `openremap/api/composite/` into
  `openremap/core/services/` (the engine), so the API is now only `@register`
  handlers + a single shared `load_binary` helper. The canonical
  `to_json_safe()` now lives in `openremap/core/serialize.py` (re-exported by
  `api/serialize.py`); service functions raise plain `ValueError` /
  `MergeConflict` and the gate translates to `GuardError`. The
  `analyze`/`convert` CLI commands now go through the API layer too.

### Fixed

- `oem_part_number` was `null` for several EDC15/EDC16 dumps that do carry
  a VAG part number (e.g. `038906019CJ`, `038906016L`) — now extracted and
  matching the external reference labels on the validation set
  (previously 4 misses, now 0).
- **Marelli IAW 1AP part number** — `oem_part_number` was always `null`; the
  extractor now resolves the 10–11 digit part-number run in the code+cal area
  (e.g. `55598889641` at 0x051C0 on the Peugeot 206 dump). Labelled
  heuristic — closed sources report the same value minus the leading 5
  (`5598889641`).

### Removed

- **Dead `openremap-server` JSON-RPC daemon** — `openremap/server.py` (the
  "OpenRemap Studio" daemon, long since superseded) is deleted, and the
  `openremap-server` console script is replaced by `openremap-api`, which
  points at the new stdio JSON-RPC transport
  (`python -m openremap.api.transport.stdio`). The wire format is unchanged
  in shape but errors are now JSON-RPC 2.0 `{code, message}` objects instead
  of bare strings; every command is dispatched through the `openremap.api`
  registry (27 methods).
